# Epic 7: Spatial Anchoring (CA-8)

**Objective:** Guaranteed-interior label anchor points for every sector — Pole of Inaccessibility (polylabel) computed in the Worker from B1.e contour segments, delivered via Transferable handoff with a sync `getAnchor` accessor.
**Scope:** Incorporates PRD §"Acceptance Criteria — Epic 7". Normative detail: ROADMAP §9 (CA-8, F-4.5, F-4.6); prerequisite A0.3 fixtures already exist (`test/fixtures/anchor-shapes.json` — schema and count verified against the file, but see the **Fixture data defect** note under Task 7.3 before treating its `expectedAnchor` values as authoritative).

**Verifiable & Measurable Success Criteria:**

- **Fixture pass:** 100% of `anchor-shapes.json` fixtures (exactly 20, covering all 7 shape classes) produce anchors within a fixed `1.0 px` tolerance of `expectedAnchor`. (The fixture schema has no per-record `tolerancePx` field — each fixture is `{id, type, points, expectedAnchor}`; 1.0 px is CA-8's default precision applied uniformly.) **Currently blocked by a verified data defect in the checked-in `expectedAnchor` values — see Task 7.3's "Fixture data defect" note; BDFL ruling required before this criterion is enforceable as written.**
- **Interiority:** every computed anchor lies strictly inside its sector's boundary — including annulus, spiral, and narrow-corridor shapes where centroids fail. On a real bootstrapped registry (Task 7.2's integration test) this is `pixelIndicesMirror[anchorY * width + anchorX] === sectorId` (Main-side check; the mirror is a flat row-major array, not anchor-indexed — `pixelIndices` itself is Worker-owned post-bootstrap, see Task 7.2). On the `anchor-shapes.json` fixtures (Task 7.3), which encode continuous-coordinate polygon rings with no pixel/bitmap data at all, this is a point-in-polygon (crossing-number) test against the fixture's ring points.
- **Handoff discipline:** `anchors` (`Int16Array`, `sectorCount·2`) allocated Worker-side on first `computeAnchors` (`INIT_ANCHORS`), delivered via the Epic 6 ring pool; `getAnchor` is synchronous.
- **Isolation:** `SimulationClock` drift ≤ ±2 ms during anchor computation.

## Tasks

### Task 7.1 — Polylabel implementation (Worker)

**PRD Reference:** §"Acceptance Criteria — Epic 7"; ROADMAP §9 CA-8 Algorithm.

**Work:**

- Implement Pole of Inaccessibility in a Worker-safe module (e.g., `src/worker/polylabel.ts`, `@internal`): quadtree cell subdivision with priority queue, point-to-boundary signed distance over the sector's contour segments (from `contourPointers`/`contourPoints`: an **unordered flat CSR list** of unit-length raster-crack segments `[x1,y1,x2,y2]` per sector — outer-boundary and hole-boundary edges are interleaved in raster-scan order with no ring grouping or connectivity guarantee; see the contour-extraction comments in `src/SectorRegistry.ts`), default precision 1.0 px. Both the point-in-polygon test (crossing-number/ray-cast) and the min-distance-to-boundary computation are ring-order-agnostic over a flat edge set, so multi-ring sectors (holes: annulus class) need no ring-separation logic — iterate every segment in the sector's flat list uniformly.
- **Map-edge gap (code-verified):** the B1.e scan emits interior cracks only (`x < width - 1` / `y < height - 1` guards in `SectorRegistry.ts`) — no segments exist along the bitmap's outer edge (`x = 0`, `y = 0`, `x = width`, `y = height`). A sector touching the bitmap edge therefore has an **unclosed** segment set, breaking both crossing-number parity and boundary distance. The anchor path must synthesize the missing map-border cracks before running polylabel (one O(2·(W+H)) pass over the border rows/columns of `pixelIndices`, which is Worker-owned post-bootstrap) — equivalently, treat out-of-bounds as boundary. All four sectors of `test-4x4.png` (2×2 quadrants) touch the bitmap edge, so Task 7.2's integration test hits this immediately; `maps/large.png` (single sector spanning the whole bitmap) has **zero** emitted contour segments without this synthesis.
- **Tie determinism:** evaluate the bbox-center initial candidate first (mapbox behavior) so tie-degenerate shapes (rectangles, symmetric multi-pole) resolve deterministically. Worker-side, do not attempt a shoelace centroid over the flat segment list — segment direction is a raster-emission artifact, not ring orientation, so the signed-area sum is meaningless; the per-sector `centroids` entry (bootstrap-transferred) is a valid extra candidate instead.
- Typed-array queue storage; `await yieldIfNeeded(state)` between cell batches (≤ 8 ms slices).
- Note (P-9): implement internally rather than adding a dependency; the algorithm is ~150 lines and the mapbox reference is the behavioral spec.

**Done when:** Node-mode unit tests against hand-computable shapes (square → center; L-shape → interior of the wider arm — give the test L unequal arm widths, since for an equal-width L the true pole sits on the inner-corner diagonal of the joint, not inside either arm) pass; multi-pole class returns a deterministic single anchor (max-distance tie broken by first-found, documented).

### Task 7.2 — `computeAnchors` / `getAnchor` wiring

**PRD Reference:** §"Public API delta".

**Work:**

- Worker handler `computeAnchors`: on first call allocate `anchors: Int16Array(sectorCount·2)` and emit `INIT_ANCHORS`; iterate all sectors (yielding), write `[x, y]` per sector — mapping each float pole coordinate to its **containing pixel with `Math.floor`** before storing in the `Int16Array`. Not `Math.round`: contour cracks live on the pixel-corner lattice, so a single-pixel sector at `(px, py)` has its pole at `(px + 0.5, py + 0.5)`, which `Math.round` would store as `(px + 1, py + 1)` — a different pixel, failing the interiority check — whereas `Math.floor` of a strictly-interior point always lands in a pixel belonging to the sector. (The `centroids` rounding in `SectorRegistry.ts` is not a comparable precedent: centroids average integer pixel-center coordinates, not corner-lattice coordinates.) Deliver via ring-pool Transferable handoff (F-4.6).
- `MapEngine.computeAnchors(): Promise<void>` (lifecycle-invalidation registered) and `MapEngine.getAnchor(sectorId: number): [number, number]` — sync read from Main-current buffer; throws before first computation completes (documented; same throw-before-ready _behavior_ as `getGroupBBox`, but **not** the same error class — `MappingRequiredError`'s documented trigger is mapping/aggregation preconditions and no parent mapping is involved here; the PRD does not name an error class for this throw, so default to a plain descriptive `Error` unless the BDFL rules otherwise).
- Update `example/src/controller.ts`: render a label/marker at each sector's anchor (this is the feature's demo and a visual regression canary), drawn as example-owned DOM overlay elements. **Projection API defect (NEEDS BDFL RULING before implementation):** The previous spec demanded using an "existing public `renderer.camera`" and map `width`/`height` for `Vector3.project()` world→screen mapping, while forbidding new public exports (PR-4). However, `MapEngine` exposes neither `camera`, `width`, `height`, nor any projection API. The example app cannot project coordinates without one of these being exposed. The BDFL must rule on how to project these coordinates (e.g., authorize exposing a projection method, expose the camera/dimensions, or drop the visual overlay requirement) before this step can be executed.

**Done when:** integration test computes anchors on the 4×4 fixture and reads them synchronously — interiority asserted via Main's `pixelIndicesMirror[anchorY * width + anchorX] === sectorId` (the only Main-resident copy; `pixelIndices` itself is Worker-owned post-bootstrap); lifecycle rejection covered; example renders anchors via `npm run example` smoke check.

### Task 7.3 — Fixture acceptance + drift

**PRD Reference:** §"Acceptance Criteria — Epic 7".

**Work:**

- Acceptance spec iterating every fixture in `test/fixtures/anchor-shapes.json`: each fixture is `{id, type, points, expectedAnchor}` — a continuous-coordinate polygon (`points`: an array of `[x, y]` vertex **pairs**, not a flat scalar list) with no pixel/bitmap/`sectorId`/`tolerancePx` field. Ring parsing has **two conventions in the same file**: the 6 multi-ring fixtures (`annulus-*`: outer + 1 hole ring; `multi-pole-*`: outer + 2 hole rings) close each ring explicitly by repeating its first vertex, rings back-to-back; the other 14 single-ring fixtures do **not** repeat the first vertex — their ring is open and must be closed implicitly (last vertex → first vertex). Parsing that expects an explicit closing vertex everywhere leaves 14 of the 20 polygons open. Call the Task 7.1 polylabel module directly (Node-mode) against each fixture's segment set (consecutive point pairs per ring, plus the closing edge per the two conventions above) — do **not** construct a `SectorRegistry`/bitmap from the fixture: several fixtures use non-integer coordinates (e.g. `convex-3`'s point `[50, 86.6]`) that cannot be rasterized onto a pixel grid. Assert `|anchor − expectedAnchor| ≤ 1.0 px` (fixed tolerance, matching CA-8's default precision — see Success Criteria note) and interiority via a point-in-polygon (crossing-number) test against the fixture's ring points.
- **Fixture data defect (verified 2026-07-07 against a reference polylabel — NEEDS BDFL RULING before this spec can go green):** the checked-in `expectedAnchor` values contradict the polylabel definition for 13 of the 20 fixtures. Three are not even interior: `concave-2` expects `[50, 50]` at signed distance **−30** (its point list `[0,0],[100,0],[100,100],[80,50],[100,0]` encloses only the thin triangle `(100,0),(100,100),(80,50)`, area 1000 — the repeated vertex is the _second_ vertex, so the shape is degenerate); `spiral-1`/`spiral-2` expect points at signed distance −10/−5, and both spiral polygons **self-intersect** under implicit closure (spiral-1's closing edge `(45,55)→(0,0)` crosses its own `x = 20` wall at `(20, 24.4)`). Ten more are interior but 2.4–70.8 px from the true pole: `annulus-1/2/3` expect mid-edge points (e.g. `annulus-1` `[12.5, 50]`, clearance 12.5, while the four corner-diagonal points reach clearance ≈ 14.64 — a 4-way tie), `concave-1` (off by 21.1 px), `concave-3` (9.5 px), `off-centroid-1/2/3` (2.43 px each — expected `[10, 10]` clearance 10 vs true pole ≈ `(11.72, 11.72)` clearance ≈ 11.72), and `multi-pole-1/2` expect the _saddle between_ the two poles (`multi-pole-1` `[50, 50]` clearance 14.14 vs true pole clearance ≈ 30). Several of the 7 records that do agree sit on exact tie sets (`narrow-corridor-*`; `multi-pole-3`'s optimum is a 60 px-long segment at clearance 20) and match only when the bbox-center/centroid candidate is evaluated first. **Do not tune the implementation to reproduce these values.** Resolution options for the BDFL: regenerate `expectedAnchor` golden-file style from an accepted reference implementation, or re-specify the assertion as interiority + clearance-optimality (`d_max − d(anchor) ≤ precision`) instead of coordinate equality.
- Concurrent-load drift test during anchor computation: `SimulationClock` drift ≤ ±2 ms (this exercises the full `computeAnchors` Worker path on a real bootstrapped registry — distinct from the Node-mode geometric-fixture pass above). The workload must demonstrably span multiple 8 ms yield slices or the assertion is vacuous — the 4×4 fixture (4 anchors, 16 px) completes in microseconds; use `test/fixtures/maps/large.png` (4096×4096, all-white single sector) with definition `{ ffffff: { name: 'All' } }` as in `test/PalettePerf.gl.spec.ts` (an empty definition yields `sectorCount === 0`, i.e. zero work; note this fixture also has zero B1.e contour segments until Task 7.1's map-edge crack synthesis runs, making it a stress test of that path too).

**Done when:** 100% fixture pass in `npm run test`; drift green; results logged in PROGRESS.md.
